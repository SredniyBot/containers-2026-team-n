# ЛР 1. Dockerfile

Из одних исходников собрали два образа: [Dockerfile.bad](../Dockerfile.bad) с шестью плохими практиками и исправленный [Dockerfile](../Dockerfile). Приложение «Заметки» на Java 21 ([app/](../app)) пишет заметки в `/data/notes.tsv`, каталог `/data` вынесен в volume.

## Запуск

```bash
docker build -t notes-app:good .
docker build -f Dockerfile.bad -t notes-app:bad .
docker run -d --name notes -p 8080:8080 -v notes-data:/data notes-app:good
```

Страница открывается на http://localhost:8080. Если Docker Hub недоступен, образ можно скачать с зеркала (`docker pull mirror.gcr.io/library/<образ>`) и вернуть ему исходное имя через `docker tag`.

## Плохие практики в Dockerfile.bad

Номера совпадают с комментариями в файле.

### 1. Тег `latest`

В день сборки под `maven:latest` лежал Maven на JDK 27, а код написан под Java 21. Завтра тег укажет на другой образ, и сборка изменится или сломается. Исправили на точные версии `maven:3.9.16-eclipse-temurin-21-alpine` и `eclipse-temurin:21.0.13_9-jre-alpine`.

### 2. Сборка и запуск в одном образе

В итоговый образ попали JDK, Maven, исходники и кэш `~/.m2`, хотя для запуска хватает JRE и jar. Лишнее увеличивает образ и добавляет программы, в которых могут найти уязвимость. Исправили многоэтапной сборкой: Maven собирает jar на этапе `build`, финальный образ на JRE забирает только jar.

### 3. `apt-get update` отдельным слоем и лишние пакеты

Docker кэширует `RUN apt-get update` отдельно, и при добавлении пакета в следующую строку возьмёт старый список пакетов. Сами curl, vim, nano и htop приложению не нужны и вместе со списком apt заняли 119 МБ. В хорошем образе пакетов нет, для HEALTHCHECK хватает `wget` из Alpine. Если пакет нужен, его ставят одной командой: `apk add --no-cache curl`.

### 4. `COPY . .` до сборки, без .dockerignore

Слой меняется при правке любого файла, и Maven заново скачивает зависимости: 158 артефактов из-за одной строки кода. В образ попали `.git` и наши локальные файлы, так же туда попадают `.env` и ключи. Исправленный Dockerfile сначала копирует `pom.xml` и скачивает зависимости, потом исходники. [Dockerfile.dockerignore](../Dockerfile.dockerignore) пускает в контекст только `pom.xml` и `src`.

### 5. Запуск от root

Уязвимость в приложении сразу даёт атакующему root в контейнере. Под с `runAsNonRoot: true` такой образ не запустит, это проверено в ЛР 4. В хорошем образе процесс работает от пользователя `app` с числовым uid (`USER 10001:10001`).

### 6. Shell-форма ENTRYPOINT

`ENTRYPOINT java -jar …` запускается через `/bin/sh -c`. PID 1 достаётся оболочке, и SIGTERM она Java не передаёт. `docker stop` ждёт тайм-аут и убивает процесс SIGKILL, запросы обрываются. В exec-форме `ENTRYPOINT ["java", …]` Java сама получает SIGTERM и закрывает сервер.

## Две плохие практики при работе с контейнером

### Хранить данные внутри контейнера

Без volume заметка пропала после пересоздания контейнера, с `-v notes-data:/data` осталась. Контейнер пересоздают при каждом обновлении образа, поэтому данные держат в volume или в базе.

### Править файлы в работающем контейнере

Правка через `docker exec … vim` пропадёт при пересоздании, а до тех пор на сервере работает не та версия, что в git. Менять нужно Dockerfile или параметры запуска и пересоздавать контейнер.

## Когда контейнеры лучше не использовать

1. Для изоляции недоверенного кода. Контейнеры делят ядро хоста, и уязвимость в нём открывает путь к хосту и соседям. Здесь нужны виртуальные машины или песочницы вроде Firecracker и gVisor.
2. Когда программа зависит от ядра, железа или ОС хоста: драйверы, Windows-программы на Linux-сервере, задачи реального времени, приложения с графическим интерфейсом. Своего ядра у контейнера нет, а пробросить в него устройства сложнее, чем поставить программу на хост или в виртуальную машину.
