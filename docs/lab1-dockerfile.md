# ЛР 1. Dockerfile

Мы собрали из одних исходников два образа. В [Dockerfile.bad](../Dockerfile.bad) шесть плохих практик, в [Dockerfile](../Dockerfile) они исправлены. Работают оба одинаково, а различаются размером, временем пересборки, правами процесса и тем, как останавливаются.

Приложение «Заметки» мы написали сами, это веб-страница и REST API на Java 21 ([app/](../app)). В этой работе заметки хранятся в файле `/data/notes.tsv`, каталог `/data` вынесен в volume.

## Запуск

```bash
docker build -t notes-app:good .
docker build -f Dockerfile.bad -t notes-app:bad .

docker run -d --name notes -p 8080:8080 -v notes-data:/data notes-app:good
```

Страница будет на http://localhost:8080, API проверяется так:

```bash
curl --data-binary "Первая заметка" http://localhost:8080/api/notes
curl http://localhost:8080/api/notes
```

Если Docker Hub недоступен, базовые образы можно скачать с зеркала Google и переименовать:

```bash
docker pull mirror.gcr.io/library/maven:3.9.16-eclipse-temurin-21-alpine
docker tag mirror.gcr.io/library/maven:3.9.16-eclipse-temurin-21-alpine maven:3.9.16-eclipse-temurin-21-alpine
```

То же нужно сделать с `eclipse-temurin:21.0.13_9-jre-alpine` и `maven:latest`, а для ЛР 2 и 4 ещё с `postgres:16.16-alpine`.

## Замеры

Мерили 20.11.2026 на Docker Desktop 29.2.1.

|  | Dockerfile.bad | Dockerfile |
|---|---|---|
| Размер образа | 660 МБ | 208 МБ |
| Пересборка после правки одной строки кода | `mvn package` 27 с, скачано 158 артефактов | `mvn package` 9 с, зависимости из кэша |
| Пользователь процесса | root, uid 0 | app, uid 10001 |
| `docker stop -t 10` | SIGKILL через 10 с, код выхода 137 | завершение по SIGTERM за 2 с, код 143 |
| Java в образе | JDK 27, его выбрал тег `latest` | JRE 21.0.13 |

Команды, которыми мерили:

```bash
docker image ls notes-app                            # размер
docker run --rm --entrypoint id notes-app:bad        # пользователь
docker build --progress=plain -f Dockerfile.bad .    # какие шаги CACHED, а какие выполнялись заново
docker stop -t 10 notes-bad                          # остановка
docker inspect -f '{{.State.ExitCode}}' notes-bad    # код выхода
```

Тайм-аут в `docker stop` задали явно. По умолчанию Docker ждёт 10 секунд, но наш Docker Desktop создавал контейнеры со `StopTimeout=1` (видно в `docker inspect`), и без `-t` плохой контейнер убивался через 1–2 секунды. Код выхода и здесь 137, то есть процесс добили SIGKILL.

## Плохие практики в Dockerfile.bad

Номера те же, что в комментариях Dockerfile.bad.

### 1. Плавающий тег `latest`

В день сборки под тегом `maven:latest` лежал Maven на JDK 27 и Ubuntu 26.04, а код написан под Java 21. Со временем тег переедет на другой образ, и та же команда соберёт что-то другое или упадёт. Выяснить, почему вчера собиралось, а сегодня нет, будет трудно: под этим тегом вчерашнего образа уже нет.

Мы перешли на точные версии: `maven:3.9.16-eclipse-temurin-21-alpine` и `eclipse-temurin:21.0.13_9-jre-alpine`. Для полной воспроизводимости к тегу дописывают ещё digest `@sha256:…`.

### 2. Сборка и запуск в одном образе

В итоговый образ попали JDK, Maven, исходники, каталог `target` и кэш зависимостей `~/.m2` на 23 МБ. Для запуска хватило бы JRE и jar. Из-за остального образ больше и дольше качается на каждый сервер, а в каждой лишней программе могут найти уязвимость. К тому же с `javac` и `mvn` под рукой атакующему проще собрать и запустить свой код прямо в контейнере.

Сборку разделили на два этапа (многоэтапная сборка). На этапе `build` Maven собирает jar, а финальный образ начинается с JRE и забирает из первого этапа только этот файл (`COPY --from=build`).

### 3. `apt-get update` отдельным слоем и лишние пакеты

```dockerfile
RUN apt-get update
RUN apt-get install -y curl vim nano htop
```

Docker кэширует слой с `update` отдельно. Если через месяц дописать пакет во вторую строку, Docker возьмёт из кэша старый список пакетов, и установка упадёт с 404 или поставит устаревшие версии. Да и сами пакеты приложению не нужны. Они заняли 74 МБ, и ещё 45 МБ остались от списка пакетов apt, который никто не удалил.

В хорошем образе дополнительных пакетов нет. Для HEALTHCHECK хватает `wget` из busybox, он в Alpine уже есть. Если пакет всё же нужен, на Alpine его ставят одной командой без кэша:

```dockerfile
RUN apk add --no-cache curl
```

На Debian и Ubuntu то же самое пишут одной инструкцией `RUN`: `apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*`.

### 4. `COPY . .` до сборки и без .dockerignore

Слой `COPY . .` меняется при правке любого файла, хоть README. Тогда Docker заново выполняет все следующие шаги, в том числе скачивание зависимостей: из-за одной строки кода Maven скачал 158 артефактов. Когда в репозитории появился этот отчёт, плохой образ снова 27 секунд выполнял `mvn package`, а хороший собрался целиком из кэша.

Ещё в `/app` оказались `.git`, оба Dockerfile и наш рабочий файл с планом, которого нет в репозитории. Тем же путём в образ попадают `.env` с паролями и ключи.

Исправленный Dockerfile сначала копирует только `pom.xml` и скачивает зависимости (`mvn dependency:go-offline`), а исходники копирует потом. Слой с зависимостями пересобирается, только когда меняется `pom.xml`. [Dockerfile.dockerignore](../Dockerfile.dockerignore) пропускает в контекст сборки только `pom.xml` и `src`. BuildKit применяет файл вида `<имя Dockerfile>.dockerignore` только к своему Dockerfile, поэтому плохого образа он не касается.

### 5. Запуск от root

`USER` не указан, и процесс работает с uid 0. Если в приложении найдут уязвимость, атакующий получит root внутри контейнера. А если вдобавок найдётся ошибка в изоляции или к контейнеру примонтирован каталог хоста, атакующий сможет выбраться на хост. Если в поде указано `securityContext.runAsNonRoot: true`, Kubernetes такой образ не запустит, мы проверили это в ЛР 4.

Пользователя `app` с uid 10001 создаём сами, отдаём ему `/data`, и дальше всё работает от него (`USER 10001:10001`). Uid записан числом, потому что по имени пользователя Kubernetes не может проверить, что это не root.

### 6. Shell-форма ENTRYPOINT

Строку `ENTRYPOINT java -jar …` Docker запускает как `/bin/sh -c "java -jar …"`. PID 1 в контейнере достаётся оболочке, Java работает её дочерним процессом, и SIGTERM оболочка ей не передаёт. `docker stop` ждёт тайм-аут и убивает всё SIGKILL. Незавершённые запросы обрываются, файл может остаться недописанным. У нас код выхода был 137 (128 + 9), а лог закончился без строки о завершении.

Достаточно записать ENTRYPOINT в exec-форме, `["java", …]`. Тогда Java сама становится PID 1 и получает SIGTERM, а наш обработчик закрывает сервер и пишет в лог:

```
2026-11-20T19:59:23.629023993Z SIGTERM received, stopping
2026-11-20T19:59:23.629948957Z stopped
```

Код выхода 143 (128 + 15) значит, что процесс завершился сам по SIGTERM. Команду `serve` мы вынесли в `CMD`, чтобы её можно было заменить при запуске. В ЛР 2 так запускается миграция.

Сверх исправлений в хорошем образе есть ещё две вещи. `HEALTHCHECK` обращается к `/health/live`, поэтому `docker ps` показывает статус `healthy`. Флаг `-XX:MaxRAMPercentage=75` отдаёт под кучу 75 % лимита памяти контейнера вместо 25 % по умолчанию. Сам лимит JVM 21 видит и без флага.

## Две плохие практики при работе с контейнером

### Хранить данные внутри контейнера

Без volume заметки пишутся в слой контейнера и живут, пока жив контейнер. Мы запустили его без `-v`, добавили заметку и пересоздали контейнер. Список оказался пуст. С `-v notes-data:/data` заметка после тех же шагов осталась. При обновлении образа контейнер всё равно создают заново, поэтому всё, что жалко потерять, держат в volume или в базе.

### Править файлы в работающем контейнере

В плохом образе есть vim, и хочется поправить что-то прямо внутри: `docker exec -it notes-bad vim …`. Правка исчезнет при первом пересоздании контейнера. До тех пор на сервере работает не та версия, что в git, и знает об этом только тот, кто правил. Менять нужно Dockerfile или параметры запуска (переменные окружения, volume), потом пересобирать образ и создавать контейнер заново. `docker restart` здесь не поможет: он перезапускает контейнер со старым образом.

## Когда контейнеры лучше не использовать

1. Когда нужно надёжно изолировать чужой код. Все контейнеры на хосте делят одно ядро, и через уязвимость в нём код из контейнера может добраться до хоста и соседних контейнеров. Поэтому недоверенный код, например в онлайн-компиляторах или сервисах, где клиенты запускают свои программы, изолируют виртуальными машинами или песочницами вроде Firecracker и gVisor.
2. Когда программа зависит от ядра, железа или ОС хоста. Это драйверы и модули ядра, Windows-программы на Linux-сервере, задачи реального времени, десктопные приложения с графическим интерфейсом. Своего ядра у контейнера нет, а пробросить в него устройства и графику сложнее, чем поставить программу на хост или в виртуальную машину.
