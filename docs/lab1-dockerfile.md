# ЛР 1. Dockerfile

Из одних исходников собрали два образа: [Dockerfile.bad](../Dockerfile.bad) с шестью плохими практиками и [Dockerfile](../Dockerfile), где они исправлены. Оба образа запускаются и отвечают одинаково. Различаются размер, скорость пересборки, права процесса и поведение при остановке.

Приложение — «Заметки» на Java 21 ([app/](../app)): веб-страница и REST API. В этой работе заметки хранятся в файле `/data/notes.tsv`, а в каталог `/data` монтируется volume.

## Запуск

```bash
docker build -t notes-app:good .
docker build -f Dockerfile.bad -t notes-app:bad .

docker run -d --name notes -p 8080:8080 -v notes-data:/data notes-app:good
```

Страница открывается на http://localhost:8080. Проверить API:

```bash
curl --data-binary "Первая заметка" http://localhost:8080/api/notes
curl http://localhost:8080/api/notes
```

Если Docker Hub недоступен, базовые образы можно взять с зеркала Google и переименовать:

```bash
docker pull mirror.gcr.io/library/maven:3.9.16-eclipse-temurin-21-alpine
docker tag mirror.gcr.io/library/maven:3.9.16-eclipse-temurin-21-alpine maven:3.9.16-eclipse-temurin-21-alpine
```

То же нужно сделать с `eclipse-temurin:21.0.13_9-jre-alpine` и `maven:latest`, а для ЛР 2 и 4 — с `postgres:16.16-alpine`.

## Итог в цифрах

Замеры сделаны 20.11.2026 на Docker Desktop 29.2.1.

|  | Dockerfile.bad | Dockerfile |
|---|---|---|
| Размер образа | 660 МБ | 208 МБ |
| Пересборка после правки одной строки кода | `mvn package` 27 с, скачано 158 артефактов | `mvn package` 9 с, зависимости из кэша |
| Пользователь процесса | root, uid 0 | app, uid 10001 |
| `docker stop -t 10` | SIGKILL через 10 с, код выхода 137 | завершение по SIGTERM за 2 с, код 143 |
| Java в образе | JDK 27 (так решил `latest`) | JRE 21.0.13 |

Как замеряли:

```bash
docker image ls notes-app                            # размер
docker run --rm --entrypoint id notes-app:bad        # пользователь
docker build --progress=plain -f Dockerfile.bad .    # какие шаги CACHED, а какие выполнялись заново
docker stop -t 10 notes-bad                          # остановка
docker inspect -f '{{.State.ExitCode}}' notes-bad    # код выхода
```

Тайм-аут остановки указываем явно: 10 секунд — стандартное значение Docker. В нашем Docker Desktop контейнеры создавались со `StopTimeout=1` (видно в `docker inspect`), и без `-t` плохой контейнер убивался уже через 1–2 секунды. Код 137 и в этом случае показывает, что процесс добили SIGKILL.

## Плохие практики в Dockerfile.bad

Номера совпадают с комментариями в самом файле.

### 1. Плавающий тег `latest`

`FROM maven:latest` на день сборки означал Maven на JDK 27 и Ubuntu 26.04, хотя код написан под Java 21. Завтра тег укажет на другой образ, и та же команда соберёт другое или не соберёт ничего. Ошибку «а у меня собиралось» потом не воспроизвести.

Исправление: точные версии `maven:3.9.16-eclipse-temurin-21-alpine` и `eclipse-temurin:21.0.13_9-jre-alpine`. Для полной воспроизводимости к тегу можно добавить digest: `@sha256:…`.

### 2. Сборка и запуск в одном образе

В рабочий образ попали JDK, Maven, исходники, каталог `target` и кэш зависимостей `~/.m2` на 23 МБ. Для запуска нужны только JRE и jar. Всё остальное увеличивает образ, замедляет его доставку на каждый сервер и добавляет программы, в которых находят уязвимости. `javac` и `mvn` в рабочем образе помогут атакующему собрать и запустить свой код прямо в контейнере.

Исправление: многоэтапная сборка. Этап `build` с Maven собирает jar. Финальный этап начинается с JRE и забирает один файл: `COPY --from=build`.

### 3. `apt-get update` отдельным слоем и лишние пакеты

```dockerfile
RUN apt-get update
RUN apt-get install -y curl vim nano htop
```

Слой с `update` кэшируется отдельно. Если через месяц дописать пакет во вторую строку, Docker возьмёт из кэша старый список пакетов, и установка упадёт с 404 или поставит устаревшие версии. Сами пакеты приложению не нужны: они заняли 74 МБ, и ещё 45 МБ занял неудалённый список пакетов apt.

Исправление: в хорошем образе дополнительных пакетов нет. Для HEALTHCHECK хватает `wget` из busybox, который уже есть в Alpine. Если пакет всё-таки нужен, на Alpine его ставят одной командой без кэша:

```dockerfile
RUN apk add --no-cache curl
```

На Debian и Ubuntu то же делается так: `apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*`, одной инструкцией `RUN`.

### 4. `COPY . .` до сборки и без .dockerignore

Слой `COPY . .` меняется при правке любого файла, даже README. Всё, что идёт после него, выполняется заново, включая скачивание зависимостей: 158 артефактов из-за одной строки кода. Проверили и правку не в коде: после того как в репозитории появился этот отчёт, хороший образ целиком собрался из кэша, а плохой снова 27 секунд выполнял `mvn package`.

Кроме того, в `/app` оказались `.git`, оба Dockerfile и даже наш локальный рабочий файл, которого нет в репозитории. Так в образ утекают `.env` с паролями и ключи.

Исправление: сначала копируем только `pom.xml` и скачиваем зависимости (`mvn dependency:go-offline`), потом исходники. Слой с зависимостями пересобирается только при изменении `pom.xml`. Файл [Dockerfile.dockerignore](../Dockerfile.dockerignore) пропускает в контекст сборки только `pom.xml` и `src`. BuildKit применяет файл `<имя Dockerfile>.dockerignore` только к своему Dockerfile, поэтому на плохой образ он не действует.

### 5. Запуск от root

`USER` не указан, процесс работает с uid 0. Если в приложении найдут уязвимость, атакующий получит root внутри контейнера. Вместе с ошибкой в изоляции или примонтированным каталогом хоста это путь наружу. Под с `securityContext.runAsNonRoot: true` такой образ в Kubernetes не запустит, мы проверили это в ЛР 4.

Исправление: создаём пользователя `app` с uid 10001, отдаём ему `/data`, переключаемся `USER 10001:10001`. Uid указан числом, чтобы Kubernetes мог проверить, что это не root.

### 6. Shell-форма ENTRYPOINT

`ENTRYPOINT java -jar …` Docker запускает как `/bin/sh -c "java -jar …"`. PID 1 в контейнере — оболочка, а Java — её дочерний процесс. SIGTERM оболочка ему не передаёт. `docker stop` ждёт тайм-аут и добивает процесс SIGKILL. Запросы обрываются на полуслове, файл может не дописаться. Это видно по коду выхода 137 (128 + 9) и по логу, который обрывается без строки о завершении.

Исправление: exec-форма `ENTRYPOINT ["java", …]`. Java становится PID 1 и получает SIGTERM. Обработчик завершения закрывает сервер и пишет в лог:

```
2026-11-20T19:59:23.629023993Z SIGTERM received, stopping
2026-11-20T19:59:23.629948957Z stopped
```

Код выхода — 143 (128 + 15): процесс сам завершился по SIGTERM, его не пришлось убивать SIGKILL. Команда `serve` вынесена в `CMD`, её легко заменить при запуске. Это понадобится в ЛР 2.

Кроме исправлений, в хорошем образе есть `HEALTHCHECK`: `docker ps` показывает статус `healthy`. JVM 21 сама видит лимит памяти контейнера, а флаг `-XX:MaxRAMPercentage=75` отдаёт под кучу 75 % этого лимита вместо 25 % по умолчанию.

## Две плохие практики при работе с контейнером

### Хранить данные внутри контейнера

Без volume заметки пишутся в слой контейнера. Мы проверили: запустили контейнер без `-v`, добавили заметку, пересоздали контейнер — список пуст. С `-v notes-data:/data` та же последовательность заметку сохраняет. Контейнер одноразовый: обновление образа означает новый контейнер, поэтому всё, что нужно сохранить, должно лежать в volume или в базе.

### Править файлы в работающем контейнере

В плохом образе есть vim, и появляется соблазн поправить что-нибудь прямо внутри: `docker exec -it notes-bad vim …`. Правка пропадёт при первом же пересоздании контейнера. Пока она жива, в продакшене работает не та версия, что лежит в git, и никто об этом не знает. Изменения вносят через Dockerfile или параметры запуска (переменные окружения, volume), затем пересобирают образ и создают контейнер заново: `docker restart` оставит старый образ.

## Когда контейнеры лучше не использовать

1. Нужна сильная изоляция чужого кода. Все контейнеры на хосте работают с одним ядром. Одна уязвимость в ядре — и код из контейнера добирается до хоста и соседних контейнеров. Недоверенный код (онлайн-компиляторы, сервисы, где клиенты запускают свои программы) изолируют виртуальными машинами или песочницами вроде Firecracker и gVisor.
2. Программа зависит от ядра, железа или ОС хоста. Драйверы и модули ядра, Windows-программы на Linux-сервере, задачи реального времени, десктопные приложения с GUI. Своего ядра у контейнера нет, а пробрасывать устройства и графику сложнее, чем поставить программу на хост или в виртуальную машину.
